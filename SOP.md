## 1. 项目概览

**Smart Meeting Minutes** 是一个 macOS 原生 App，把会议录音自动转化为结构化、可落地的会议纪要，并沉淀为个人知识 Wiki。

采用**绞杀者模式（Strangler Pattern）**：

- **Swift / AppKit 壳**（Xcode 工程 `Smart Meeting Minutes`）：负责原生 GUI、配置持久化（UserDefaults）、API Key 保管（Keychain）、以及把 Python 引擎当子进程调用。壳内源文件：
  - `AppDelegate`（含「知识库」菜单，切到 LLM Wiki 分页 / 触发重建）；
  - `MainContainerViewController`（单窗口分页容器：左侧栏切换 纪要生成 / LLM Wiki / 设置；顶部**唯一「保存」按钮**转发给当前可保存分页（仅纪要生成页可保存）；默认显示 LLM Wiki）；
  - `GenerateViewController`（分页①：拖放区 + 选音频 + 开始/取消生成 + 左侧 `MarkdownEditorView` 预览/编辑纪要；**不再含「导入 RAG 文档」**（v2.0 起移至 Wiki 页））；
  - `WikiViewController`（分页②：左列表 Wiki 首页置顶 + **多选** + 右 `MarkdownEditorView`；工具栏 = 搜索栏 + Wiki 首页/重建/刷新/打开文件夹/＋新增/**📥 导入会议纪要**/**🗑 删除选中**；右键菜单「删除」、⌘Backspace 批量删）；
  - `MarkdownEditorView`（**TipTap 引擎驱动的真·所见即所得编辑器**（ProseMirror 系，MIT，离线内置 `Resources/tiptap/tiptap.bundle.js` ~540KB，无外部网络依赖；Vditor 作为可回退引擎仍保留，由 `editorEngine` 切换）。默认 **Typora 式真 WYSIWYG**：Markdown 源码符号默认不显示、`[[页面]]` 真双链（输入 `[[` 自动完成、缺失页红字、hover 预览）；`editorBridge` 协议 `save / wikilink / getPages / wikilinkPreview`；供纪要预览与 Wiki 编辑复用）；
  - `SettingsViewController`（分页③：whisper.cpp 文件夹选择、模型档位选择+下载、自定义提示词、恢复默认）；
  - `PipelineRunner`（通用子进程运行器）、`SetupWizard*`、`AppConfig`、`KeychainHelper`、**`AppAlert`**（统一 `NSAlert` 封装 + SF Symbols 图标，所有弹出式通知经此发出）。
  - （**已删除**：`ViewController.swift`、`WikiWindowController.swift`——分页化后不再需要独立主窗口/独立 Wiki 窗口。）
- **Python 引擎**（`PythonEngine/pipeline.py`）：负责实际业务——音频转写（whisper）、脱敏、LLM 精炼纪要、Wiki 生成。
- 两者通过**环境变量 + JSON 通信**解耦（详见 `Swift_Python_Interface_Contract.md`），Swift 不直接 import Python。

## 6. Swift ↔ Python 接口契约（摘要）

> 完整契约见仓库根 `Swift_Python_Interface_Contract.md`，本节仅记要点。

- **调用**：`PipelineRunner`（NSTask/Process）以 `pythonExecutable [script] [--json-log ...]` 启动子进程。默认 `script = AppConfig.pipelineScript`（pipeline.py）；Wiki 功能传入 `005_LLMWiKi/wiki_build.py` / `wiki_query.py` 以运行非 pipeline 脚本。
- **LLM Wiki 分页（`WikiViewController`，分页②）调用的 Python 入口**：
  - 页面列表：`pipeline.py --list-wiki-pages` → stdout JSON `[{name,type,file,aliases}]`（按类型+名称排序，v2.0 起含 `aliases`）。Swift 在列表**最前强制插入「Wiki 首页」**（文件 `005_LLMWiKi/Wiki_首页.md`），其余来自 JSON。
  - 内容预览：直接读 `005_LLMWiKi/wiki_pages/<file>`（或首页 `Wiki_首页.md`）（不另跑命令）；读入后交给 `MarkdownEditorView` 渲染，支持 `[[双链]]` 点击跳转；预览顶部渲染 **frontmatter 约束 banner**（v2.0：type/canonical_name/aliases/company/title/中文名/source/summary/tags/updated，不显示 backlinks）。
  - 搜索：`005_LLMWiKi/wiki_query.py "<查询>" --top 8` → stdout 人类可读文本（语义检索，缺模型时退化为关键词）；结果以**只读**形式显示，不可编辑/保存。
  - 重建 Wiki（App 按钮，v2.0.1 起）：`pipeline.py --build-index`——**仅重建 Wiki 首页（MOC）导航页**，纯本地、无出网、不碰 RAG 向量库；幂等（内容不变则不重写）。这是用户日常点「重建 Wiki」该做的事。⚠️ **历史垃圾人物页的根因在脱敏映射**：`004_Desensitize_Cache/global_desensitize_mapping.json` 里曾被本地人名探测误标出大量 `[PERSON_x]` 垃圾 token（一个/一定/我不会/跟俞云…），每次跑流程（`auto_stub_new_entities` 或 `wiki_build.py`）都会把它们重建为人物页。治本 = 清映射母体 + `auto_stub` 姓氏守卫双防（见 §8）。已实际清理：794 → 117 页、诊断 0 候选。
  - **重型「页面生成 + RAG 重建」**：`005_LLMWiKi/wiki_build.py`（事实→结构化页面 + 向量/反链索引；首次需下载 bge 模型 ≈90MB）。⚠️ **Wiki 页生成 与 RAG 索引是两回事**：`wiki_build.py` 两者都做；`--build-index` 只做首页、不动 RAG；`--import-docs` 只做 RAG 素材入库。日常不要用 `wiki_build.py` 当「重建 Wiki」按钮（v2.0 之前按钮误绑它，导致每次点都重跑 LLM+RAG，既慢又易再生垃圾页）。
  - 刷新索引：`pipeline.py --build-index`（生成 Wiki 首页 MOC）+ `pipeline.py --normalize-wiki`（统一页格式）。
  - 新增页：`pipeline.py --add-wiki-page '<JSON>'`（键：type/canonical_name/aliases/summary…）。
  - **导入纪要**：`pipeline.py --import-docs '<path>'`（`WikiViewController.importMinutes()` 经 NSOpenPanel 多选文件/目录，`--json-log` 模式）→ `import_documents()`：多格式经 pandoc/原生转 markdown，明文落 `003_Meeting_Minutes/imported_docs_<ts>/`、脱敏稿落 `005_LLMWiKi/knowledge_base/imported_docs_<ts>/`、重建向量库（v2.0 从 Generate 页迁移至此，按钮名「📥 导入会议纪要」）。
  - **删除页（v2.0）**：`pipeline.py --delete-wiki-page '<JSON>'`（键：`names:[...]`）→ `delete_wiki_pages()` 逐个删 `.md` 并调 `_clean_cross_references()` 清除邻居页的 aliases/反链、重建首页；Swift 侧多选/右键/⌘Backspace 收集行后调此命令。
  - 编辑/保存页（仅纪要生成分页可保存）：MainContainer 顶栏**唯一「保存」按钮**触发 `MarkdownEditorView` 退出编辑并把源码回传 `GenerateViewController`，宿主**直接写回**纪要 `.md` 文件；Wiki 分页**无保存按钮**（Wiki 页改完即落盘，v2.0 起不再有 Wiki 自己的「保存」）。
  - 双链跳转（v2.0 多策略匹配 `resolveWikiPage`）：在右侧预览点击 `[[某页面]]`，宿主优先按 ① 文件名去 `.md` ② 严格等值（不区分大小写）③ 半角/全角括号+全角空格归一 ④ aliases 命中——逐级回退查找并切换，解决 `[[AMD（超威半导体）]]` 半角括号不匹配 `AMD（超威半导体）.md` 的「文件不存在」。
- **入参（环境变量，契约 §2）**：`MM_BASE_DIR`、`MM_LLM_PROVIDER`、`MM_LLM_MODEL`、`MM_LLM_SYSTEM_PROMPT`（可选，自定义系统提示词，来自设置页）、`GEMINI_API_KEY`/`OPENAI_API_KEY`(+`MM_LLM_API_KEY`/`MM_LLM_BASE_URL`)、`WHISPER_CLI`、`WHISPER_MODEL`、`MM_WHISPER_ENGINE`。
- **自动重建 Wiki（会议纪要后 + 导入手写纪要后）**：`main()` 在每轮会议纪要成功生成（`completed>0`）后、`import_manual_minutes()` 在导入成功后，均自动以子进程调用 `005_LLMWiKi/wiki_build.py`（与 GUI「重建 Wiki」按钮等价），无需手动点按钮即把新会议事实沉淀进个人 Wiki 并重建向量库/反链/首页。失败仅告警、不影响纪要。可用 `MM_AUTO_WIKI=0` 关闭。
- **进度（stderr，JSON-Lines，契约 §5）**：每行 `{"level":...,"msg":...,"step":...,"progress":0..1}`，Swift 逐行解析驱动原生进度条。
- **结果（stdout 末尾 JSON）**：`PipelineRunner.parseTrailingJSON` 取末行 JSON 作为业务结果。
- **铁律**：错误回调必须把 **stderr 原文**带回 UI（光给退出码＝让用户猜谜）；Swift 仅经 env + 子进程 + JSON 通信，密钥只走 Keychain→env。

## 8. 常见问题 / 坑位

- **`xcodebuild` 必须用 `CODE_SIGNING_ALLOWED=NO` 兜底**：沙箱/无开发者证书时直接 `build` 会卡签名；加该组参数可出未签名 app 用于本地调试。仅 `swiftc -parse` 不够（不做语义/类型检查），改完 Swift 务必跑完整 build。
- **pipeline 退出码 1 / 找不到输入**：先查 `MM_BASE_DIR` 是否指向含 `001_Audio` 的目录；pipeline `main()` 从 `Config.AUDIO_DIR` 按 `*.m4a/*.mp3/*.wav/*.aac` glob，目录名错了就空跑。看 stderr 真实 Python 报错定位。
- **`ModuleNotFoundError: No module named 'numpy'`（退出码 1）**：app 误用了无 numpy 的解释器。**根因**：`AppConfig.pythonExecutable` 的回退路径若指向 `/usr/bin/python3`（macOS 自带 3.9.6，无 numpy）即触发。已修复为回退 `/usr/local/bin/python3`（3.11，含 numpy）。排查：在 App 内确认 `PYTHON_EXECUTABLE` 未误设为旧 python；或临时在 UserDefaults 显式设 `/usr/local/bin/python3` 验证。
- **LLM 生成 404 `models/gemini-2.5-flash is no longer available to new users`**：`gemini-2.5-flash`（及 2.5-pro / 2.0-flash 等）自 2026 年起对新用户停用。**已修复**：① pipeline 默认模型改为 `gemini-3.5-flash`（Gemini 3.x，官方替代）；② pipeline 新增「停用模型自愈重映射表」，若 UserDefaults 仍持久化旧名（如 `gemini-2.5-flash`）会自动重映射到 `gemini-3.5-flash` 并打 stderr 告警，无需手动清设置；③ Swift 向导模型下拉框已换成 `gemini-3.5-flash / gemini-3.1-flash-lite / gemini-3.6-flash`。仍报 404 时，可在 App 模型设置或 `MM_MODEL` 环境变量换用其他 3.x 模型（如 `gemini-3.6-flash`）。
- **`RAG 检索失败: replace() argument 2 must be str, not None`**：脱敏函数里 `text.replace(word, tag)` 的 `tag` 为 `None` 导致崩溃。**根因**：实体字典（`005_LLMWiKi/staff_mapping.txt`、`company_directory.txt`）由代码写成**裸词条**（每行一个词、无 `->` 占位符），`load_dict_file` 对裸词条返回 `None`；尚未分配到占位符的裸词条进入 RAG 脱敏 / step6 还原时就触发 `replace(str, None)`。**已修复**：在两处 `.replace(word, tag)` 循环加 `if word and tag` 守护，裸词条未拿到占位符则跳过（不崩溃，仅该词本次不被脱敏）。注意：若日志持续报此错，需检查实体字典是否混入了异常行。
- **目录命名不一致 = 丢数据或空跑**：任何新建/改名必须同步 §4 四处（pipeline Config / 向导 `createStandardSubdirs` / 主窗口读写 / 导出脚本）。
- **pipeline 退出码 6 + Metal 断言 `add_dense_scalar_long_long`（Read-only bytes bound to write-access shader arg）**：这是 **sentence-transformers 在 Apple Silicon 的 MPS(Metal) 后端做 embedding 时的硬崩溃**，属 Metal 层 abort，Python try/except 捕获不到，进程直接以非 0 退出。stderr 里通常伴随 `Loading weights ...` 后突然崩。**已修复**：所有 embedding 模型统一经 `_load_embedding_model()` 强制 `device="cpu"`（bge-small-zh-v1.5 极小，CPU 推理足够快且绝对稳定），并设 `TOKENIZERS_PARALLELISM=false` / `PYTORCH_ENABLE_MPS_FALLBACK=1`。**红线**：任何新增 embedding 调用都必须走 `_load_embedding_model()`，严禁直接 `SentenceTransformer(...)` 重踩 MPS 崩溃。
- **删除用户目录前先只读扫描**：确认是否为空、是否含真实数据；非空或含数据一律走废纸篓（`~/.Trash/`），绝不直接 `rm -rf`。
- **每次会议纪要跑完自动重建 Wiki（默认开启）**：`main()` 末尾对有成功生成的会议自动跑 `005_LLMWiKi/wiki_build.py`（云端组织页面 + 本地建向量库/反链/首页）；无 `GEMINI_API_KEY` 时自动退化为本地启发式，异常仅告警不影响纪要。若想跳过自动重建（如仅做快速本地测试），设 `MM_AUTO_WIKI=0` 即可，手动「重建 Wiki」按钮仍可用。
- **GUI 是单窗口分页容器（v1.8）**：`MainContainerViewController` 用左侧栏按钮切换 纪要生成/LLM Wiki/设置 三分页，全部在窗口内切换、不再弹新窗口；顶部「保存」按钮转发给当前可保存分页（`SaveablePage` 协议）。纪要预览与 Wiki 编辑都复用 `MarkdownEditorView`（WKWebView + 内嵌离线 JS 渲染 Markdown 与 `[[双链]]`）。改 UI 时：新增分页 = 在 `MainContainerViewController.buildPages()` 注册 VC + 在 `tabDefs` 加按钮；`MarkdownEditorView` 的渲染/双链逻辑全在 `MarkdownEditorView.swift` 内嵌 HTML 模板里（改样式/解析改这里，无需动 WKWebView 设置）。
- **AppKit 布局编译坑（v1.8 单窗口重构时踩到，记此避免重踩）**：① `NSView` 只有 `setContentHuggingPriority(_:for:)`；`setHuggingPriority(_:for:)` 仅 `NSStackView` 有，给普通 `NSView`（如容器 `body`）调用会编译报 `no member 'setHuggingPriority'`，必须改用 `setContentHuggingPriority`。② `NSScrollView` 没有 `contentLayoutGuide`（那是 `NSView` 的 macOS 11+ 属性，NSScrollView 上不存在）；`documentView` 应约束到 `scroll.contentView`（如 `stack.widthAnchor.constraint(equalTo: scroll.contentView.widthAnchor)`），并把 `documentView.translatesAutoresizingMaskIntoConstraints = false`，否则约束冲突或内容不滚动。③ 一个方法若既被 `#selector`（需 `@objc`）引用、又作为 Swift 协议 witness（如 `WikiViewController.saveCurrent()` 既要 `#selector(saveCurrent)` 又要满足 `SaveablePage` 协议），写 `@objc func saveCurrent()` 即可两者兼得——`@objc` 不影响其作为普通 Swift 协议方法。④ **激活约束前父子视图必须已在同一个视图树（运行期崩溃，v1.9）**：`NSLayoutConstraint.activate` 要求约束两端有共同祖先，否则抛 `NSGenericException: ... no common ancestor` 并在 `viewDidLoad` 直接崩溃。两个典型误触：a) 给按钮设 `b.widthAnchor.constraint(equalTo: sidebar.widthAnchor)` 时按钮还没 `sidebar.addArrangedSubview(b)` → 顺序必须是**先 addArrangedSubview 再激活宽度约束**；b) 在容器里激活 `sidebar.leadingAnchor.constraint(equalTo: body.leadingAnchor)` 这类约束前没 `body.addSubview(sidebar)`/`body.addSubview(contentView)` → 顺序必须是**先把子视图 addSubview 进 body，再激活 body 内约束**。任何 `*.widthAnchor/*.heightAnchor.constraint(...)` 若引用了尚未入树的视图都会炸。⑤ **纯代码 AppKit 必须删掉 storyboard 主界面（v1.9）**：分页化删除 `ViewController.swift` 后，若 pbxproj 仍残留 `INFOPLIST_KEY_NSMainStoryboardFile = Main` 且 Main.storyboard 还在，AppKit 会在启动时自动加载已引用已删类的 storyboard，报 `Unknown class '_TtC...14ViewController'` 并把旧窗口树叠在纯代码 window 上，引发连环崩溃。修复 = 从 pbxproj 删除该 build setting + 删除废弃 Main.storyboard + `rm -rf ~/Library/Developer/Xcode/DerivedData/Meetinsight-*` 清掉旧构建缓存后全新构建（旧 DerivedData 里仍会残留旧的 storyboardc 与旧类，必须清）。⑥ **Xcode 17 Debug Dylib 拆库会让 `@main` 入口失效、App 启动后无任何窗口（v1.9.1）**：Xcode 17 默认把 App 代码编译进 `Smart Meeting Minutes.debug.dylib`、主二进制退化成只调 `NSApplicationMain` 的薄壳，且该薄壳**不引用 `AppDelegate`**（dylib 也没有 `LC_MAIN`），于是 `@main` 生成的「把 `AppDelegate` 设为 delegate」的入口不被执行 → `applicationDidFinishLaunching` 永不触发、窗口永不创建。现象极具迷惑性：控制台只剩系统级 `linkd.autoShortcut` / `Process Instance Registry` 噪声 + `applicationSupportsSecureRestorableState:` WARNING（均与 App 无关），极易误判为「旧 App」「崩溃」或「系统噪声可忽略」。诊断铁证（无头环境也能做）：`otool -L` 主二进制无 dylib 依赖、`nm -a` 主二进制无 `AppDelegate` 符号、`applicationDidFinishLaunching` 开头写文件标记也始终不创建。修复 = 在 Debug/Release 构建设置加 `ENABLE_DEBUG_DYLIB = NO`，让 App 回归传统单一 Mach-O 二进制（`@main` 正常当入口，已用 `strings` 确认二进制内含 `_TtC21Meetinsight11AppDelegate` 且被 `NSApplicationMain` 引用）。**任何 Xcode 17 工程只要用 `@main` + AppKit，都必须关掉 Debug Dylib**，否则必现「启动无窗口」。**但 v1.9.1 仅回归单二进制、并未真正修复**：根因是移除 storyboard 后 `@main` 合成入口未能可靠触发 `applicationDidFinishLaunching`（无头无法验证、Xcode 运行则窗口不显示）。**真正根治（v1.9.2）= 抛弃 `@main`，改显式 `main.swift` 入口**：`let app = NSApplication.shared; let delegate = AppDelegate(); app.delegate = delegate; app.setActivationPolicy(.regular); app.run()`——`app.delegate` 是字面赋值，`didFinishLaunching` 必被调用，彻底消除入口歧义。⑦ **无头沙箱无法验证 GUI 启动**：本机 `Bash` 直接运行 .app 二进制时 stdout/系统日志均被丢弃、且 `applicationDidFinishLaunching` 不会触发（无 WindowServer），故任何"无头启动测试"都不能作为 App 是否工作的证据；GUI 启动与否只能由用户在 Xcode ⌘R / 双击 .app 实测。改完 `rm -rf ~/Library/Developer/Xcode/DerivedData/Meetinsight-*` 全新构建。⑧ **`NSJSONSerialization` 不接受 Swift String 当顶层容器（v1.9.3）**：往 WebView / JSON RPC 注入 Swift `String` 时若用 `JSONSerialization.data(withJSONObject: aString)`，**100% 抛 `NSInvalidArgumentException: Invalid top-level type in JSON write`**，因为 `NSJSONSerialization` 顶层只接受 `Array`/`Dictionary`（即便传 `.fragmentsAllowed` 也只放宽 NSNumber 写法，不接受 String）。**正确做法**：顶层 String 用 `JSONEncoder().encode(s)`（返回 `Data`，内容是 `"escaped"`），Array/Dict 顶层才用 `JSONSerialization`。我们 `MarkdownEditorView.jsString(_:)` 的 bug 就是这个：把 `markdown`（普通 String）直接丢给 `JSONSerialization`，一选 Wiki 页就崩。⑨ **`NSSplitView.heightAnchor == 父栈.heightAnchor` 是必冲突的反模式（v1.9.3）**：把 `NSSplitView` 放进 `NSStackView` 子视图时**绝对不要**给 split 加 `heightAnchor.constraint(equalTo: stack.heightAnchor)`（或 `widthAnchor` 对横向栈同理）——父栈里装着 split 自己，这条等高数学上不可能满足，AppKit 会解不开并持续打 `Unable to simultaneously satisfy constraints` + 用 break constraint 兜底，且会随子视图内容增减触发一片 `Stack.Min(>=X)` / `Edge >=0` 冲突告警。正确做法：split 想横/纵向填满父栈时，靠 `split.setContentHuggingPriority(.defaultLow, for: 该轴)` 让父栈默认的 `.fill` 分布自动把剩余空间让给 split。
- **`[[双链]]` 别名 `[[name|alias]]` 必须按 `|` 拆：左为跳转目标、右为显示文字（v1.9.4）**：此前 `MarkdownEditorView` 内嵌 JS 的 `inline()` 把整段 `name|alias` 当 `data-name` 跳转目标，导致点 `[[ADI (亚德诺) |ADI]]` 跳去找「ADI (亚德诺) |ADI」这一整串页名 → 找不到页报错。**已修复**：解析时 `raw.split('|')`，`target = seg[0].trim()`、`label = seg[1]?.trim() ?? target`，只把 `target` 写进 `data-name`。改写 Markdown→HTML 的双链解析与 HTML→Markdown 的 `htmlToMd()` 回写都要同步按此规则，否则编辑态保存会把别名「吃掉」。
- **WYSIWYG 必须用「单 contenteditable + 实时 debounce 渲染」，不要「预览 div + 隐藏 textarea 互换」（v1.9.4）**：用户要的是所见即所得编辑——点一下不是「预览变新编辑窗」，而是原地进入编辑、边打字边渲染。实现 = `#editor` 单 `<div contenteditable="true">`，用 `.render`/`.editing` class 切换只读渲染/可编辑态；`input` 事件触发 `scheduleRender()`（180ms 防抖，先把当前 HTML 经 `htmlToMd()` 还原成 markdown 存盘、再重渲染），`enterEdit()` 在进编辑态时把渲染后的 HTML 还原成 markdown 灌回同一 div；Esc/⌘S 退出编辑并 `requestSave()`。切勿回到「点开新窗口 = 用 textarea 重新编辑原始 markdown」的旧交互。
- **`MM_QUIET_STDERR=1` 是 macOS `linkd`/剪贴板/TCC 系统噪声唯一可控的静默手段（v1.9.4）**：`linkd.autoShortcut`、`Process Instance Registry`、`pboard`、`TCC` 这类 stderr 噪声来自 macOS 系统框架，App 代码、entitlements、沙箱都无法消除（除非整 App 签名并关闭系统日志域）。唯一用户可控的办法是启动期把 fd 2 重定向到 `/dev/null`：`main.swift` 在 `applicationDidFinishLaunching` 之前读 `MM_QUIET_STDERR` 环境变量，为 `"1"` 时 `open("/dev/null", O_WRONLY)` + `dup2(devnull, STDERR_FILENO)`。需要调试时设 `MM_QUIET_STDERR=0` 或不设即可恢复 stderr。
- **主窗口自适应大小靠 UserDefaults 持久化 + `didResizeNotification`（v1.9.4）**：默认 `1280×820`（最小 `1100×720`），`showMainWindow()` 读 `MM_WINDOW_WIDTH`/`MM_WINDOW_HEIGHT`（无则默认），按 `NSScreen.main.visibleFrame` 居中；挂 `NSWindow.didResizeNotification` 把实时尺寸写回 UserDefaults，下次启动沿用。改窗口默认尺寸只动这两个常量与 `AppDelegate.showMainWindow()`，不要硬编码在别处。
- **embedding 模型加载必须「离线优先」，否则公司网/沙箱代理会把 HuggingFace Hub 请求劫持成 `502 Bad Gateway`（v1.9.5）**：`bge-small-zh-v1.5` 权重已缓存在 `~/.cache/huggingface`，本地 CPU 推理**本不需要联网**；但 `SentenceTransformer(name)` 默认会向 HF Hub 发请求校验 revision/拉 config，一旦环境有 `HTTPS_PROXY`（公司代理、或 agent 沙箱透明代理 `127.0.0.1:xxxx`）就会返回 `502`，RAG 重建直接崩。**已修复**：`_load_embedding_model()` 改为 `SentenceTransformer(name, device="cpu", local_files_only=True)` 优先离线加载；仅当本机从未下载过该模型（`LocalEntryNotFoundError`）才退化为联网下载一次。这也顺带让 RAG 重建在受限网络下快且稳。
- **`import_documents` 重建 RAG 时 `kb_items` 必须带 `content`/`name`，且 `_kb_md_files()` 必须扫 `imported_docs_*` 子目录（v1.9.5）**：v1.9.4 的导入功能有两处隐患——① `_kb_md_files()` 只 glob `KB_DIR/*.md` + `imported_minutes/`，导入稿落在 `KB_DIR/imported_docs_<ts>/` 子目录**根本没被索引**；② `import_documents` 里构造的 `kb_items` 漏了 `content` 键，而 `_rag_query` 内部 `it["content"].split(...)` 会 `KeyError`。两处叠加导致「RAG 重建成功但索引 0 文件」。**已修复**：`kb_items` 补 `name`+`content`（与其他两处调用方一致），`_kb_md_files()` 新增遍历 `imported_docs_*` 子目录。现已验证导入 2 个样本后向量库真正写入 2 个 chunk。
- **RAG 自动建人物页的识别门槛必须「姓氏白名单 + 词频门槛 + 语境过滤」三件套，否则会炸出海量无意义页（v2.0）**：v1.x 的 `auto_stub_new_entities` 用了过松的中文名启发式——只要「2~3 个汉字 + 末尾是称谓」就建页，结果把「鸡鸡四/金元/吧对/这样你/长高一」这类噪声也建成了真人 Wiki 页（数百个垃圾页）。**已修复（铁律红线，改命名实体识别别再松绑）**：① `_looks_like_cn_name` 要求**首字（或复姓前两字）必须落在 `_CN_SURNAMES` 常见姓氏白名单**，并拒 `_CN_ROLE_WORDS` 角色词后缀 / `_CN_ROLE_TRIGRAMS` 三字组；② `_cn_honorific_names` **删掉**了噪声「动词后缀」正则（如「对 X 说/和 X 一起」误抓），仅保留「称谓/引号/「叫/是 X」」等可靠语境，并按 `_CN_HONORIFIC_SUFFIX` 动态剥称谓后缀；③ `_en_name_candidates` 要求英文名人名**出现 ≥2 次**；④ `detect_candidate_names` 对中文名加**词频门槛**（`MIN_OCCURRENCES = 1` 当全文 ≤500 字，否则 `=2`）。任何想「让更多名字被自动收录」的改动，只能收紧不能放宽——宁可漏收真名，也不要再产生垃圾页。
- **`[[双链]]` 跳转必须「文件名优先 + 半角/全角括号归一」，否则半角括号链接点不开（v2.0）**：`[[AMD（超威半导体）]]` 在源 markdown 里用全角括号 `（`、但 frontmatter `canonical_name` 是 `AMD`、文件名是 `AMD（超威半导体）.md`、而别名不含带括号展示名，旧逻辑按 `canonical_name`/别名匹配 → 找不到 → 报「文件不存在」。**已修复**：`WikiViewController.resolveWikiPage` 匹配优先级 = ① 文件名去 `.md` ② 严格等值（不区分大小写）③ `normalizeForWikiMatch`（半角→全角括号、全角空格→半角）归一后等值 ④ `aliases` 命中；`--list-wiki-pages` 同时返回 `aliases` 供第④级用。改双链解析时这四级顺序别动。
- **Wiki 列表删除是「多选 + 右键 + ⌘Backspace」三入口，删前必须清邻居反链并重建首页（v2.0）**：`WikiViewController` 表格 `allowsMultipleSelection=true`；`deleteSelected()` 收集选中行（排除首页行 0）→ NSAlert 确认 → `pipeline.py --delete-wiki-page '{"names":[...]}'` → `delete_wiki_pages()` 逐个删 `.md` 后调 `_clean_cross_references()` 把被删名从邻居页 `aliases`/反链里剔掉并 `_sync_wiki_to_dicts` + 重建首页。**注意**：删除走 CLI 而非直接 rm，绝不能为了「快」在 Swift 侧直接删文件——否则邻居页里的 `[[双链]]` 与反链会悬空。
- **内嵌 JS 的 `//` 注释绝不能含换行转义，否则整段编辑器脚本崩溃、Wiki 预览全白（v2.0.1）**：`MarkdownEditorView` 的 HTML 模板是 Swift `"""` 多行字符串，`\n` 在 Swift 里是真实换行。若一段 `//` 行尾评论里写了 `\n`（想折行），浏览器端 `//` 注释**不跨行**，下一行被当成可执行代码，且残留反引号会开一个未闭合模板字符串 → 整个 `<script>` 语法错误 → `renderMarkdown` 等函数全未定义 → 右侧预览对所有 Wiki 页/纪要全白。**铁律**：内嵌 JS 注释要么单行 `//`，要么用 `/* ... */` 多行；绝不在 `//` 注释里放 `\n`。改 `MarkdownEditorView` 模板后用 `node --check` 抽出 `<script>` 块验证语法再交付。
- **「重建 Wiki」与「RAG 重建」是两件事，按钮别再绑错（v2.0.1）**：用户原话「Wiki 页和 RAG 并不是一回事」。`wiki_build.py` = 页面生成（LLM 组织）+ 向量库/反链索引（RAG）一起做；`--build-index` = 只重建 `Wiki_首页.md` 导航页（纯本地、无网）；`--import-docs` = 只把外部文档入库做 RAG。App「重建 Wiki」按钮现在只调 `--build-index`（首页），不再触发 `wiki_build.py` 重型流程。批量清理历史垃圾页用 `pipeline.py --diagnose-wiki`（只读）先确认、再 `--delete-wiki-page` 删除。
- **AppIcon 必须填充，否则弹窗 / Dock / 窗口全破图（v2.0.2）**：`Assets.xcassets/AppIcon.appiconset` 的 10 个尺寸槽（16/32/128/256/512 @1x/@2x）若 `filename` 全空，构建出的 `.app` 既无 Dock/窗口图标，`NSAlert` 未显式设 `icon` 时也会回退成破图。**已修复**：从 `PythonEngine/app/icon_source.png`（1024²）用 `sips -z` 生成 16/32/64/128/256/512/1024 PNG 填槽并写回 `Contents.json`；同时所有 `NSAlert` 改用 `AppAlert` 显式设 SF Symbols 图标，双重保险不再破图。换图标只改 `icon_source.png` 重跑 sips 即可。
- **Vditor 资源必须放在 Xcode 同步源组之外；构建后由 Xcode Run Script Phase 自动拷（v2.1.1 起）**：编辑器改用离线内置 Vditor（整包 `Smart Meeting Minutes/vditor/`，~5.5MB）。① **绝不能放进 `PBXFileSystemSynchronizedRootGroup` 覆盖的源目录**——该组会把目录下所有文件自动收编进 build 且**拍平嵌套结构**，于是 `vditor/dist/...` 被压成 `Contents/Resources/dist/...`，Vditor 按 `dist/` 相对路径找 lute/highlight 全部 404、编辑器不渲染。正确做法：把 `vditor/` 放在工程根（与 `.xcodeproj` 同级、在同步源组之外）。② **v2.1.1 起** xcode 工程已自带 **「Copy Vditor」Run Script Build Phase**（`shellScript` 内 `cp -R "${PROJECT_DIR}/vditor" "${BUILT_PRODUCTS_DIR}/${UNLOCALIZED_RESOURCES_FOLDER_PATH}/vditor"`）+ target 设 `ENABLE_USER_SCRIPT_SANDBOXING = NO`，Xcode Run / `xcodebuild` 都会自动拷，不需要手工 `cp -R`。**v2.1 时期的「Run Script 阶段不可靠」结论已不成立**（当时是因 sandboxing=YES + WorkBuddy Bash shim 清掉 `BUILT_PRODUCTS_DIR`；现在前者改 NO，Run Script 走 Xcode 内部进程路径不受 Bash shim 影响）。③ 改编辑器后**务必校验** `Contents/Resources/vditor/dist/index.min.js` 与 `dist/js/lute/lute.min.js` 存在；若不存在先 `rm -rf ~/Library/Developer/Xcode/DerivedData/Meetinsight-*` 再 Run。
